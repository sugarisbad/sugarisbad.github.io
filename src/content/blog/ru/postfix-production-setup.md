## Сначала роль сервера и DNS

Postfix принимает, маршрутизирует и отправляет письма. Для чтения почты по IMAP и хранения пользовательских ящиков обычно нужен ещё Dovecot, для фильтрации и DKIM-подписи — например, Rspamd. До установки пакетов определитесь: это почта сотрудников, отправка уведомлений из приложения или промежуточный SMTP-релей. От этого зависят открытые порты, авторизация и схема доставки.

Для сервера, который принимает и отправляет почту напрямую, нужны постоянный публичный IP, доступный TCP/25 и возможность задать PTR у провайдера. Проверяйте ограничения хостинга заранее: открытый порт в firewall не снимает блокировку исходящего SMTP на стороне площадки.

Узел должен представляться полным именем вроде `mail.example.com`. Его A-запись указывает на IP сервера, PTR этого IP — обратно на то же имя, а MX домена — на почтовый узел. Пример для одного IPv4-адреса:

```text
example.com.       IN MX 10 mail.example.com.
mail.example.com.  IN A     192.0.2.10
```

`192.0.2.10` — адрес для документации: замените его своим. PTR настраивается у владельца IP, обычно в панели VPS-провайдера. IPv6 подключайте вместе с рабочей маршрутизацией, PTR и SPF: одна AAAA-запись ещё не делает почтовый тракт готовым.

## Закройте relay и разделите порты

Open relay — сервер, который позволяет любому отправлять через него письма на чужие домены. Правила пересылки задавайте отдельно от антиспама, через `smtpd_relay_restrictions`. Для современной установки Postfix 3.6+ базовый фрагмент выглядит так:

```ini
# /etc/postfix/main.cf — фрагмент
myhostname = mail.example.com
mynetworks = 127.0.0.1/32 [::1]/128

smtpd_relay_restrictions =
    permit_mynetworks,
    permit_sasl_authenticated,
    reject_unauth_destination

# AUTH включим только на клиентском порту submission
smtpd_sasl_auth_enable = no
```

В `mynetworks` оставляйте только действительно доверенные адреса. Целая сеть хостинга или Docker-подсеть «чтобы приложение заработало» даёт право пересылки всем узлам внутри неё. Для приложений лучше отдельные SMTP-учётные записи.

TCP/25 нужен для обмена между почтовыми серверами. Клиенты отправляют почту через TCP/587 с STARTTLS или TCP/465 с TLS сразу после соединения. Список обслуживаемых доменов тоже задаётся явно: `mydestination` для локальных доменов либо соответствующие virtual/relay-карты для выбранной схемы. Публикация MX сама по себе не учит Postfix принимать почту для домена.

## TLS и авторизация — по назначению

На публичном MX обычно включают STARTTLS в режиме `may`: сервер предлагает шифрование, сохраняя совместимость с внешними отправителями. На submission шифрование и авторизация обязательны. Не переносите `encrypt` на весь входящий TCP/25 без понимания последствий — отправители без TLS перестанут доставлять вам почту.

```ini
# /etc/postfix/main.cf — фрагмент для Postfix 3.6+
smtpd_tls_security_level = may
smtp_tls_security_level = may
smtpd_tls_chain_files = /etc/postfix/tls/mail.pem
smtpd_tls_mandatory_protocols = >=TLSv1.2
smtpd_tls_auth_only = yes

smtpd_sasl_type = dovecot
smtpd_sasl_path = private/auth
smtpd_sasl_security_options = noanonymous
```

В `mail.pem` сначала идёт закрытый ключ, затем сертификат сервера и промежуточные сертификаты. Файл принадлежит root и имеет права `0600`. Продление сертификата должно атомарно заменять этот файл и выполнять `postfix reload`. Сокет Dovecot `/var/spool/postfix/private/auth` настраивается отдельно, с доступом для пользователя Postfix.

Для TCP/587 добавьте или отредактируйте существующую службу в `master.cf`:

```text
# /etc/postfix/master.cf
submission inet n - n - - smtpd
  -o smtpd_tls_security_level=encrypt
  -o smtpd_sasl_auth_enable=yes
  -o smtpd_relay_restrictions=permit_sasl_authenticated,reject
```

Это фрагменты конфигурации, а не готовый почтовый стек: сертификат, база пользователей, сокет авторизации и карты получателей должны существовать. Для TCP/465 нужна отдельная служба с `smtpd_tls_wrappermode=yes`. Параметры `smtp_*` относятся к исходящему клиенту Postfix, `smtpd_*` — к серверу, принимающему соединения.

Если почта уходит через фиксированный внешний relayhost, задайте для него обязательный TLS с проверкой сертификата и имени узла. Режим `may` для прямой доставки по MX — совместимый базовый вариант, но не защита от понижения уровня шифрования. Для более строгой межсерверной политики отдельно внедряют DANE с DNSSEC или MTA-STS.

## SPF, DKIM и DMARC: настройте всю цепочку

SPF перечисляет разрешённые источники отправки, DKIM подписывает сообщение, DMARC проверяет согласование домена в видимом `From` с доменом успешной SPF- или DKIM-проверки. Три TXT-записи без работающей подписи и проверки маршрутов задачу не решают.

Для одного отправляющего IP стартовая DNS-конфигурация может выглядеть так:

```text
example.com. IN TXT "v=spf1 ip4:192.0.2.10 -all"
_dmarc.example.com. IN TXT "v=DMARC1; p=none; rua=mailto:dmarc@example.com"
```

Такой SPF подходит, только если с домена отправляет этот сервер. Добавьте CRM, сервис рассылок и другие легитимные источники в одну SPF-запись, прежде чем включать `-all`. Несколько независимых записей `v=spf1` для одного имени создают ошибку проверки.

DKIM настраивайте через Rspamd или OpenDKIM, подключённый к Postfix через Milter. Для RSA используйте ключ 2048 бит и отдельный селектор, например `mail2026._domainkey.example.com`. Проверьте подпись и у писем от SMTP-клиентов, и у сообщений, отправленных приложением локально.

DMARC начинайте с `p=none` и реально работающего ящика для агрегированных отчётов. Когда учтены все источники отправки, переходите к `quarantine`, затем к `reject`. Сам `p=none` ничего не блокирует. В тестовых письмах смотрите `Authentication-Results` у получателя: ожидаемый результат — `spf=pass`, `dkim=pass` и `dmarc=pass`.

## Антиспам и лимиты: смотрите в обе стороны

Для входящей почты настройте фильтрацию и корректный список получателей. Несуществующий ящик лучше отклонять во время SMTP-сеанса, чем принимать сообщение и потом отправлять возврат на подделанный адрес. С catch-all этот контроль теряется, поэтому включайте его только под конкретную задачу.

Для исходящей почты нужны лимиты по учётной записи или приложению. Их можно реализовать через policy service или возможности фильтра. Ограничение соединений по IP и fail2ban полезны против перебора паролей, но не заменяют контроль отправки от уже авторизованного пользователя.

На submission привяжите допустимые envelope-from адреса к логинам через `smtpd_sender_login_maps` и подходящую проверку соответствия. Это не проверяет автоматически видимый заголовок `From`: если требуется ограничить и его, добавьте отдельную политику в фильтре.

Бесконечный <code>postqueue -f</code> не исправляет неправильный DNS, отказ получателя или украденный пароль. Сначала найдите причину по queue ID и ответу удалённого сервера.</div>

## Очередь, бэкапы и конфигурация как код

Минимальный набор команд после изменения конфигурации:

```bash
sudo postfix check
postconf -n
postqueue -p
```

`postfix check` проверяет часть локальных настроек и прав, `postconf -n` показывает переопределённые параметры, `postqueue -p` — очередь и причины задержек. После проверки примените изменения через `sudo postfix reload`. Ни одна из этих команд не заменяет внешний тест приёма, отправки и запрета relay.

Мониторьте размер очереди и возраст самого старого отложенного письма, свободное место и inode, ошибки авторизации, срок действия TLS-сертификата. Порог выбирайте под обычный объём почты. Добавьте проверку полного маршрута: приложение → SMTP → тестовый ящик. О подходе к алертам подробнее — в [статье про Prometheus и Grafana](/blog/prometheus-grafana-monitoring/).

Конфиги и шаблоны DNS держите в Git, пароли и закрытые ключи — отдельно. В зашифрованный бэкап включайте настройки, DKIM-ключи, данные пользователей и почтовые ящики, если они хранятся у вас. Восстановление проверяйте на отдельной машине; ориентир — [проверяемые бэкапы с restic](/blog/backups-321-restic/).
